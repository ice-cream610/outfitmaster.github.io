# 继续开发的接口与状态约定

## 方案是版本，不是一张图片

`Outfit` 同时保存 `id / productIds / lockedIds / selectedIds / avatar / conditions / imageTaskId`。`generate()` 接收当前版本和修改请求，返回**完整的新版本**。页面在成功前保留旧版本；失败不更换商品或图片。`AbortController` 与当前任务引用共同阻止旧结果覆盖新状态。

现阶段效果资源由 `previewCell()` 按完整商品组合和形象映射，只开放已登记的 18 个精选形象组合；推荐、替换、形象切换和历史恢复均校验该映射，拒绝缺图组合。接入后端后，应把这层改为每个方案自己的已完成图片任务 URL，不以数组序号猜图。

## 保留 UI，替换服务适配器

`OutfitService` 当前提供 `generate(request, signal)` 与 `checkout(outfit, specs)`。建议新增 `HttpOutfitService` 实现同一接口，后端返回可校验的方案；页面的锁定、替换、失败恢复和购买清单交互可继续使用。

以下为建议接口，不是已经上线的服务：

| 接口 | 建议职责 |
| --- | --- |
| GET /api/products | 授权商品源、真实 SKU、价格、库存、商品链接 |
| POST /api/outfit-jobs | 接收 baseVersion、来源/预算/锁定与单件修改，创建任务 |
| GET /api/outfit-jobs/:id | 推荐/生图进度、失败信息、完整方案结果 |
| POST /api/saved-outfits | 保存方案及关联会话，按登录用户隔离 |
| POST /api/purchase-preview | 再验证 SKU 与价格库存，返回逐项错误与平台交接地址 |
| POST /api/events | 记录曝光、调整、收藏、点击；订单回传后才记录成交 |

服务器必须重新校验所有客户端约束，价格不能信任前端传值。真实模型的 ID 必须在可用货盘中，锁定项必须保留，同类别替换不隐式改动其他品类。建议给任务携带 baseVersion 与请求 ID，保证乱序返回可被丢弃。

## 推荐下一轮开发顺序

1. 先用这套 UI 接入少量有授权的商品与真实数据服务。
2. 用真实推荐服务替换有限关键词逻辑；任何文本输出必须回到结构化修改请求。
3. 接入异步生图，专项验证身份、服饰颜色与版型一致性；建立失败与成本监控。
4. 增加账号与方案/会话存储，替换 localStorage。
5. 接入单个商家的加购/结算交接及订单归因，再做业务验证。
